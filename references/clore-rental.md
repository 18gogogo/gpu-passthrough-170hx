# Clore rental — setup, whitelist, economics (244 rig)

Extracted from gpu-passthrough SKILL.md (2026-09-20).

## Rental
- Platforms auto-start/stop containers per customer rental — do NOT run long-lived "rental daemon" containers.
- A card can be listed on ONE platform at a time (unlist from A before listing on B).
- Rental only works in Docker (nvidia) mode; switch to vfio before serving a VM rental.
- Vast.ai hard requirements include public IPv4 + forwarded ports — Tailscale does NOT count as public IP.
- **Clore pricing + unit economics (244 rig):** user lists at $18/day on-demand, $12/day spot (set in the dashboard, not by host command). Card power_limits range is [100,300]W (per client/gpu_specs.json) — 160W is fine, below 100W is out of platform range. CORRECTED economics (an early pass mixed HKD costs with USD revenues and wrongly concluded "structurally unprofitable" — always convert to ONE currency before P&L): at 150-160W limit, revenue per GPU-hr after fees ≈ US$0.169 (on-demand, 10% fee) / US$0.122 (spot, 2.5%), marginal electricity per rented GPU-hr ≈ HK$0.22-0.28 (≈US$0.03-0.036) → **each rental hour is profitable** (~+HK$0.7-1.1/GPU-hr); the real cost is fixed idle electricity (~HK$600-1,000/month unrented, CLP 2026 tier 3-4 + monthly FCC). Break-even on-demand ≈ US$3-3.5/day for all 4 cards at 150-160W — user's $18 is well above it. Vast.ai ruled out (needs public IPv4 + port forwarding). **vLLM (vllm-qwen) on GPU 0 stays RUNNING by user priority** — tenants see 3/4 GPUs free, user accepts that; NEVER stop their vLLM "to free a GPU for rental" without asking (agent did, user corrected). Partial rental is normal: ~20% of market servers list only some cards, a user-held card does not block renting the rest.
- **Clore.ai on this rig (verified 2026-09-20):** installed at /opt/clore-hosting (agent repo hosting/clore_hosting, systemd unit `clore-hosting.service`, active — rentals live since 2026-09-20). Start: `sudo systemctl start clore-hosting` (verify `systemctl is-active clore-hosting` = active); stop: `sudo systemctl stop clore-hosting`. The agent ITSELF manages the `clore-monitor-*` docker container (spawns per rental, exits when idle — RestartPolicy=no, Exited(137) is normal) — never docker start/stop that container by hand; if one lingers after stop, `docker stop <name>`. Auth lives in /opt/clore-hosting/client/auth (root-owned, 0600). The container NAME embeds the Clore token — never write it into docs/chat. data.img (loop device, ~500GB) is the agent's storage — do not delete. Before renting: cards must be in nvidia mode (gpu-to-host.sh first); before VM passthrough: stop clore-hosting first.
- **⚠️ CRITICAL PITFALL (2026-09-20): Clore agent DELETES your other containers + images.** Symptom: user's own containers (portainer, qwen38-vllm) + their images vanish while Clore is active — the agent does it on purpose, not a disk accident. Root cause (verified in /opt/clore-hosting/hosting/ source): (1) docker_deploy.py deploy() every loop stops+removes any running container NOT in rental list AND NOT in ALLOWED_CONTAINER_NAMES env (within ~1s of creation); (2) main.py handle_container_cache() prunes non-rental images (max 2/run) — images vanish gradually; (3) Clore install moved the ENTIRE /var/lib/docker onto its own data.img (xfs 480GB) — agent owns the docker data root. **Fix (applied + verified 2026-09-20):** whitelist via TWO mechanisms — (a) containers: add `Environment=ALLOWED_CONTAINER_NAMES=portainer,qwen38-vllm,vllm-qwen` to /etc/systemd/system/clore-hosting.service (backup first) + `systemctl daemon-reload && restart clore-hosting`, verify with `cat /proc/$(systemctl show -p MainPID --value clore-hosting)/environ | tr '\0' '\n' | grep ALLOWED`; (b) images: /opt/clore-hosting/extra_allowed_images.json = `[{"repository": "portainer/portainer-ce", "allowed_tags": ["latest", "*"]}, {"repository": "vllm/vllm-openai", "allowed_tags": ["latest", "*"]}, {"repository": "lazymio/vllm-backport", "allowed_tags": ["v0.12.0-sm80", "*"]}]` (format from lib/utils.py get_extra_allowed_images). Restart = ~10-30s rental offline (user accepted; do off-peak if revenue matters). **Recovery after agent already deleted things:** re-pull images + recreate containers (portainer_data volume survived → Portainer settings preserved; vLLM image = 13GB re-pull). **Rule:** on any machine running Clore, NEVER assume your own containers/images are safe while the agent is active — check `docker ps -a` + `docker images` after every Clore restart, and extend the whitelist whenever you add a new long-lived container. Full reset-rebuild runbook: clore-docker-recovery skill + /home/ubuntu/ok/gpu/Docker鏡像重拉重建清單.md (the doc drifts — a monthly cron re-verifies it against live state and asks the user before updating).
- **System disk is the bottleneck (verified 2026-09-20):** the rig's only disk is a 1TB SATA SSD at ~90% — data.img 480GB (Clore's docker root, fixed) + /home ~176GB (models dominate) + /var ~62GB, ~89GB free; tenant image pulls + user work will exhaust it. Agreed plan: user buys ONE extra 1TB drive (NVMe preferred ~HK$1,300-1,800 vs SATA ~$600-800), mount it (e.g. /mnt/data), `rsync` /home/ubuntu/models over, re-point the vLLM container's model mount path, then remove the old copy. Do NOT move data.img (Clore agent owns it mid-flight; moving needs agent stopped + docker downtime). RAM 128→256GB was ruled out — market data shows system RAM adds no rental price (4090: 128GB and 64GB list at the same median). agent running ≠ listed. Verify in order: (1) `systemctl is-active clore-hosting`; (2) whitelist live in the RUNNING process, not the unit file — `tr '\0' '\n' < /proc/$(systemctl show -p MainPID --value clore-hosting)/environ | grep ALLOWED` (a unit-file edit without daemon-reload+restart is NOT in effect); (3) `sudo ss -tnp | grep <agent-pid>` — one persistent ESTAB to api.clore.ai:443 (Cloudflare IP) = registered + connected; (4) `nvidia-smi -L` shows all cards (nvidia mode); (5) public IPv4 via `curl -s https://api.ipify.org`. If all pass and the dashboard still doesn't list, the gap is the web dashboard (server state / price), not the host — go to clore.ai, don't re-toggle systemctl. A GPU held by the user's own whitelisted container (e.g. vllm) is protected from agent pruning but NOT rentable — tell the user the trade-off, don't silently stop their container.
- **Reading agent logs:** there are NO log files under /opt/clore-hosting — the only log is the unit's journal stdout. It is buried under the agent's `sudo iptables -S` poll (a pam_unix/sudo line pair every 1-2s) — ALWAYS filter: `journalctl -u clore-hosting --since "1h" --no-pager | grep -viE "iptables|pam_unix"`. A `GOING TO REMOVE <image>` line repeating every second = the image-prune loop failing to delete (usually because the image is in use by a running container) — noise, not an error. auth file must be exactly 81 chars (32+48+1) or hosting.py exits with "no credentials configured" and the service.sh loop retries forever silently.
- `clore-update.timer` ships disabled; enabling it lets the agent auto-update (Clore's own design, harmless) — mention to the user, don't disable unasked.
- **Pricing review workflow (run when the user asks to compare market prices / before re-pricing):** `curl -s https://clore.ai/webapi/marketplace/servers` (no auth) → `all_servers[]`; filter `specs.gpu` by card type; per-GPU-hr = `price.on_demand.USD-Blockchain` / n / 24 (price is WHOLE-SERVER USD/day — pro-rata only matters when partial-GPU rental is on). Platform fees: spot 1.8-2.5%, on-demand 5-10%. Baseline snapshot + electricity cost model + monthly review checklist live in the user's wiki `/home/ubuntu/ok/wiki/concepts/clore-170hx-rental-market.md` (tariffs: `clp-2026-tariff.md`) — refresh the baseline THERE, don't duplicate market numbers in this skill. A monthly cron `clore-market-monthly` (1st 09:00, delivers to the user) runs `python3 /home/ubuntu/.hermes/scripts/clore-market-snapshot.py` which saves a dated raw snapshot to the wiki, diffs vs the previous one, and auto-detects the user's live HK listing price (USER_LIVE_PRICE line) — the user re-prices dynamically, so never hardcode $18 in reports or scripts. Clore auto-re-detects disk capacity/speed at every heartbeat — after an NVMe upgrade nothing is re-registered on the host; just verify the dashboard shows the new specs.
