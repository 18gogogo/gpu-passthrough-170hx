# Faulty card vs faulty slot — diagnosis (170HX rig)

Extracted from gpu-passthrough SKILL.md (2026-09-20).

## Diagnosing a faulty card (faulty card vs faulty slot)
- **GSP booter error codes in dmesg / guest kern.log:**
  - `Booter failed ... error code: 0x31` repeated ~75 times per card at boot = NORMAL with the patched cmpunlocker driver on this rig — all 4 cards log it and still initialize to 64GB. Do NOT treat it as a fault; the switch script's pre-flight warning about it is noise.
  - `Booter failed ... error code: 0x15` + `Max GSP-RM boot attempts exceeded: 4/4` + `Cannot initialize GSP firmware RM` + `RmInitAdapter failed! (0x62:0xffff:2119)` = the card's GSP firmware cannot boot in this environment. On a cmpunlocker v0.3 host in GUEST mode this is the known v0.3 VFIO gap (NOT a card fault — v0.4 fixes it, see Worked example); on a v0.4 host it means a genuine card fault (or the slot/riser it sits in). The card still appears in `lspci`, keeps a correctly assigned 64GB BAR, and may even show `Kernel driver in use: nvidia` — `nvidia-smi` simply lists N-1 cards.
- **Guest kernel log access:** `dmesg` inside the guest often fails (kernel.dmesg_restrict); `/var/log/kern.log` is readable and contains the full NVRM boot trace — grep it for `NVRM|GPU[0-9]|Booter`.
- **PCIe link check (rules out slot / CPU lane allocation):** `lspci -s <bdf> -vvv | grep -E 'LnkCap|LnkSta'`. A healthy GA100 link is x4 @5GT/s (x16 on a full-width slot). If the failing card's slot negotiates a clean link at its design width while the card still faults (e.g. GSP boot failure), the slot and CPU lane allocation are exonerated — the fault is in the card (or its GSP firmware). A degraded link (x1, 2.5GT/s, unexpected downgrade) points at the slot/riser/adapter instead.
- **Card swap test (isolates card vs slot):** physically swap the suspected card with a known-good card between slots, reboot, re-run the passthrough test. Fault follows the card → card is bad. Fault stays in the slot → slot/riser/M.2-adapter is bad. Record the BDF↔physical-card mapping BEFORE and AFTER the swap — the mapping changes with the swap, and the host BDF→guest BDF mapping comes from the VM XML (hostdev source→guest address pairs).
- **VM IP drift:** a rebuilt VM may lose its fixed IP (DHCP assigns a new one). Never trust the tracker's IP — verify with `virsh domifaddr <vm>` before SSHing.
- **Worked example (this rig's slot↔card map — the user moves cards often, re-verify after every swap):** current map: bus 0a = C card, bus 0b = D card, bus 41 = R5 340X (host display — NEVER pass through), bus 42 = B card (x8 slot, PCIe 2.0 x4), bus 43 = A card (x16 slot, PCIe 2.0 x16). History: the GSP-boot fault (0x15) first appeared only in GUEST mode on the A card at bus 43 while the same card initialized fine in host nvidia mode; after a full reshuffle (C→0a, R5 340X→41) all four cards — A included — initialized in host mode. Later, the A card at bus 43 ALSO failed GSP boot in HOST mode after a hot rebind from vfio-pci (unbind → nvidia bind while the system was up) — the fault is no longer guest-mode-specific, and a hot rebind may leave GSP in a bad state that a plain reboot may not clear; a physical power cycle is the discriminating test (card fault vs hot-rebind artifact). So the fault is position/topology-dependent, not a dead card. The clean x16 LnkSta on bus 43 exonerates the slot's LINK, but a definitive A↔B swap test is still the only proof of card-vs-slot. RESOLVED (2026-09-20, cmpunlocker v0.4): the 'exactly one card fails in guest mode' pattern was NOT a card/slot fault — it was cmpunlocker v0.3 lacking VFIO passthrough support: binding a card to vfio-pci lost its GSP boot-time registers, so the guest's GSP could not boot (0x15) and exactly one card dropped per guest boot (which card varied). v0.4 fixes it (udev rule + gsp-restore.py restores the registers on every vfio-pci bind; cmp_no_bus_reset.ko blocks the bus reset). Verified: all 4 cards at 64GB in the guest, only benign 0x31 Booter noise. If 0x15 reappears in a guest, first check the host runs cmpunlocker v0.4+ with /usr/local/lib/cmpunlocker/gsp-restore + the udev rule present (see references/cmpunlocker.md).
